# 물품별 동적 스키마

기존 화면에서는 등록 프롬프트와 Python 모델이 우산의 손잡이 등 같은 필드를 모든 물품에 반환했고 React도 정해진 목록을 그대로 표시했습니다. 현재 화면은 초안에 적용된 스키마의 필드만 표시합니다. 코트에 손잡이는 없으며, 브랜드처럼 의류에 적용되는 값이 비어 있으면 ‘미확인’으로 표시합니다.

## 공식 분류와 사진에서 관찰한 유형

`data/categories.json`에 저장된 경찰청 API 대분류 21개와 소분류 85개를 사용합니다. 자동 테스트는 CSV의 코드, 이름, 상하위 관계가 JSON과 일치하는지 확인합니다. 경찰민원24 웹사이트의 선택 옵션과의 일치는 검증하지 않았습니다.

백엔드는 공식 코드와 상하위 관계를 검증합니다. 코트나 우산처럼 사진으로 공식 소분류를 확정하기 어려우면 후보와 미확정 상태를 반환합니다. 착용 대상의 성별이나 유류품·무주물 여부는 담당자가 확인합니다. 트렌치코트, 장갑, 접이식 우산 같은 관찰 유형은 공식 분류와 별도로 보존합니다.

## 스키마 구성

모든 물품에는 공식 대분류, 공식 소분류, 물품명, 관찰된 유형, 수량이 공통 적용됩니다. 관찰 유형과 공식 분류가 양립하면 관찰 유형 특화를 적용합니다. 다음 순서로 공식 소분류 특화, 대분류 기본 서식, 일반 서식을 적용합니다.

| 범위 | 적용 대상 |
| --- | --- |
| 대분류 기본 | 가방, 도서용품, 서류, 산업용품, 스포츠용품, 자동차, 전자기기, 지갑, 컴퓨터, 휴대폰, 의류, 현금, 유가증권, 증명서, 귀금속, 카드, 쇼핑백, 악기, 유류품, 무주물, 기타물품 |
| 자동차 소분류 | 자동차열쇠, 네비게이션, 자동차번호판, 기타용품, 임시번호판 |
| 관찰 유형 특화 | 트렌치코트, 목도리·장갑, 우산, 휴대폰, 스마트키, 신용카드, 현금, 가방, 지갑 |
| 일반 | 공식 분류나 특화 항목을 정하기 어려운 물품 |

`backend/policies/item_schemas.json`의 필드 정의에 식별자, 한국어 표시명, 자료형, 필수 여부, 설명, 선택지, 추출 출처, 기본 공개 범위를 지정합니다. API는 스키마 식별자와 버전, 필드 표시 순서, 값, 근거, 검증 상태, 최종 공개 범위를 반환합니다. React는 이 응답으로 문자, 숫자, 선택, 참·거짓 및 권종별 반복 입력을 표시합니다. 기존 자료형을 이용하는 스키마를 추가하려면 선언 파일을 편집한 뒤 백엔드를 다시 시작합니다.

## 에이전트 흐름과 기존 데이터

Registration Agent는 기존 로컬 VLM으로 물품명과 관찰 유형을 먼저 인식합니다. 공식 분류 매핑과 스키마 선택 후 해당 스키마의 특징만 VLM에 요청하고 PaddleOCR의 근거를 결합합니다. Evidence Tracker가 값과 근거를 정리하고 LangGraph에서 Verification Agent와 Privacy Agent가 검증을 수행합니다. Supervisor가 결과를 모으며, 필요한 경우 Adaptive Question Agent가 추가 확인 항목을 표시합니다. 워크플로와 모델 호출 함수에 한국어 docstring을 추가했습니다.

담당자가 공식 분류나 관찰 유형을 변경하면 현재 서식에 적용되는 값만 이어받습니다. 필드를 편집하고 **수정 및 재검증**으로 검증과 개인정보 검사를 다시 실행합니다. 공개 공고에는 검증된 공개 후보만 사용합니다. 카드 식별정보 원문은 구조화 속성에서 제외하고, 민감 유형의 원본 사진은 공개하지 않습니다. 현금 권종과 정확한 총액은 본인확인용으로 관리합니다.

새 속성과 스키마는 기존 DB의 JSON 열에 저장합니다. 이전 초안은 조회할 때 현재 스키마로 표시하며 DB 열을 변경하거나 기존 게시 공고를 일괄 수정하지 않습니다.

## 코드 위치와 테스트

| 영역 | 파일 |
| --- | --- |
| 분류 및 스키마 | `backend/categories.py`, `backend/item_schemas.py`, `backend/policies/item_schemas.json`, `backend/schemas.py` |
| 에이전트 및 공개 정책 | `backend/workflow.py`, `backend/models.py`, `backend/model_diagnostics.py`, `backend/privacy.py`, `backend/policies/privacy.json` |
| API 및 DB 호환 | `backend/api.py`, `backend/service.py` |

| 회귀 테스트 | `tests/test_dynamic_schemas.py`, `tests/test_api.py`, `frontend/e2e/workflow.spec.ts` |

백엔드 테스트는 9개 유형의 합성 VLM 응답으로 공식 코드, 스키마, API, 개인정보 정책을 검증합니다. Playwright는 Mock Mode에서 공개 목록, 승인·등록 흐름과 우산에서 코트로 변경할 때 편집 및 분석 화면이 바뀌는지 검증합니다. 실제 모델의 이미지 인식 결과는 이 테스트들과 별도로 확인합니다.

PostgreSQL을 포함한 백엔드 회귀 테스트 38건과 Chrome Playwright 시나리오 4건이 통과했습니다. 프론트엔드 빌드도 성공했습니다. 기본 테스트 실행에서는 `LAF_TEST_REAL=1`이 필요한 실모델 스모크 테스트 1건을 건너뛰었으며 실모델은 아래 사진들로 별도로 검증했습니다.

실모델 검증은 별도 SQLite DB에서 실행했습니다. 기존 코트·우산·전구 사진은 원본 초안을 변경하지 않고 읽었습니다. 추가 회귀 검증에는 공개 사진을 사용했으며 카드에는 가상의 번호와 이름만 넣은 이미지를 사용했습니다. 실제 서비스는 기존 `.env`를 유지하고 프로젝트 루트에서 실행합니다. 이전 인스턴스가 같은 포트를 사용 중이면 해당 실행 터미널에서 Ctrl+C로 종료한 뒤 다시 시작합니다.

```powershell
.\start.ps1 -PythonPath .\.venv-real\Scripts\python.exe -BackendPort 18000
```

브라우저의 `http://127.0.0.1:5173`에서 사진을 등록하고 분석 결과의 공식 후보, 관찰 유형, 표준화 필드, 공개 미리보기를 확인합니다. 추가 실제 물품 사진의 검증과 85개 소분류의 특화 필드 확장은 개별 품질 확인 후 진행할 수 있습니다.
