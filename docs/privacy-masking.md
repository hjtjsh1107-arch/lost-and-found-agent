# 개인정보 탐지와 공개 검사

## 처리 범위

텍스트 규칙은 VLM 결과, PaddleOCR 문자, 메모, 정규화한 물품 필드, 제목·설명, 담당자 입력에 적용합니다. `backend/policies/privacy.json`은 탐지 유형과 부분 가림, 공개 범위, OCR 신뢰도 기준을 관리합니다. 한글 이름과 문맥에 따라 의미가 달라지는 값은 로컬 LLM이 필드 또는 OCR 조각 번호로 추가 표시합니다. 로그에는 피사체와 식별자 원문을 기록하지 않습니다.

담당자 메모에는 `가○○`, `010-****-****`, `***@example.invalid`처럼 필요한 가림 표시에 한해 부분값을 표시할 수 있습니다. 공개 본문에는 부분값도 가리며, 부정수령에 이용될 수 있는 현금 총액이나 지갑 내용물은 본인확인용으로 분리합니다. 카드 전체 번호·CVC·유효기간·주민등록번호 등 고위험 값은 구조화 필드에서 제거합니다. 저장되는 초안에는 형태, 탐지 유형, 가림 표시만 남깁니다.

## 사진 검증과 담당자 검토

1. 업로드 사진을 방향 보정한 PNG로 다시 만들며 EXIF를 제거합니다.
2. PaddleOCR 좌표, 인접 OCR 조각에서 발견한 식별자, LLM이 표시한 OCR 조각, OpenCV 얼굴 영역, 담당자 영역을 하나의 좌표계에 기록합니다.
3. Pillow가 탐지 영역을 여백과 함께 불투명한 사각형으로 덮습니다. 별도의 PNG 후보에 대해 OCR, 얼굴 및 남은 문자 문맥을 재검사합니다.
4. 시각 판단, OCR, 얼굴 검출기 또는 후속 검사에서 안전성을 확인하지 못하면 전체 가림 미리보기로 대체하고 사진 게시를 차단합니다. 카드·신분증의 민감 식별자로 판정된 사진은 해당 정책에 따라 공개를 차단합니다. 검사가 된 부분 가림 결과는 담당자 화면에서 확인할 수 있습니다.
5. **AI 분석 및 검증** 또는 **공고 검토 및 승인**에서 **마스킹 사진 보기**를 누릅니다. 비교가 허용된 건에는 원본도 표시됩니다. 사진 위에서 드래그하거나 좌표를 입력해 **추가 마스킹 및 재검사**를 누릅니다. 기존 영역에 새 영역을 누적하며 이전 승인을 무효화합니다.
6. 게시 시 코드는 텍스트 검사, 담당자 승인, 공개 본문의 승인 지문, 사진별 검증 상태, 공개 후보 해시 및 원본과의 구분을 다시 검사합니다. 공개 API는 인증된 공개 사진 바이트만 반환합니다.

사진 공개를 선택할 수 없는 경우 텍스트 검사와 담당자 승인에 성공한 공고는 사진 없이 게시할 수 있습니다. 사진을 공개하려면 승인할 때 사진 포함을 선택합니다.

## 원본 보관과 기존 데이터

초안의 원본 이미지와 공개 후보는 별도 DB 열에 저장하며 담당자 인증을 거칩니다. 고위험 영역이 탐지되거나 안전성을 확인하지 못한 원본은 담당자 비교에도 제공하지 않습니다. 게시되면 원본을 삭제합니다. 게시 전 원본을 폐기하려면 담당자 인증으로 `POST /staff/drafts/{id}/discard-originals`에 최신 `revision`을 전달합니다. 원본과 공개 후보가 제거되고 사진 기반 재검증은 종료됩니다. 진행 중인 메모의 원문은 프로세스 메모리에만 두므로 처리 중 서버가 재시작되면 입력을 다시 제출해야 합니다.

탐지 및 승인 정보는 기존 초안의 JSON 열에 추가됩니다. 초기화 시 별도 DB 열 변경이 필요하지 않습니다. 기존 초안을 게시하려면 새 정책으로 재분석하고 승인합니다. 기존 공고는 목록과 번호 조회로 유지합니다. 기존 사진의 공개 해시가 없으면 공개 API에서 제공하지 않으며 이전 체계의 텍스트 인덱스는 검색에서 제외합니다.

## 개발 파일과 확인 방법

| 파일 | 역할 |
| --- | --- |
| `backend/privacy.py`, `backend/policies/privacy.json` | 규칙 기반 탐지, 표시용 및 공개용 가림, 공개 텍스트 검사 |
| `backend/photo_privacy.py`, `backend/images.py` | OCR 영역 연결, 얼굴 검출, 불투명 렌더링, 재검사와 이미지 해시 |
| `backend/workflow.py`, `backend/models.py`, `backend/schemas.py` | LangGraph 에이전트 실행, 맥락 판정과 안전한 진단 메타데이터 |
| `backend/api.py`, `backend/service.py` | 담당자 API, 수동 마스킹, 폐기, 승인 지문, 공개 조회·게시 |
| `frontend/src/masking.tsx`, `frontend/src/workflow.tsx` | 탐지 결과, 원본과 공개 후보 비교, 드래그·키보드 입력, 재검사 |
| `tests/test_privacy_masking.py`, `tests/test_real.py`, `frontend/e2e/workflow.spec.ts` | 합성 개인정보, 실제 모델 스모크 테스트, Chrome 업무 흐름 |

합성 테스트 사진은 `python scripts/make_privacy_fixture.py`로 재현할 수 있습니다. 유형별 동적 서식과 공식 분류, 에이전트 함수 설명은 [동적 물품 스키마 문서](dynamic-item-schemas.md)에 정리했습니다.

### 통합 검증 결과

- PostgreSQL을 포함한 기본 pytest 테스트 65건이 통과했습니다. 로컬 모델 실행이 필요한 선택 테스트 2건은 기본 실행에서 제외했습니다.
- Chrome에서 React 업로드, 수정, 수동 마스킹, 승인, 게시 및 통합 목록을 검증했습니다. React 빌드와 Python 패키지 의존성 확인에 성공했습니다.
- 실제 PaddleOCR로 가상 카드의 번호와 성명 영역을 탐지하고 불투명 부분 마스킹을 적용했습니다. 다시 OCR을 적용했을 때 탐지 규칙에 걸리는 영역은 없었습니다. 정책상 가상 카드 사진도 공개하지 않았습니다.
- 실제 VLM으로 분석한 전구에 대해 담당자 API에서 전자기기 › 기타용품 분류와 습득 장소를 보완한 뒤 재검증했습니다. 가상 메모의 이름과 전화번호가 탐지됐으며 PostgreSQL에서 승인·게시·통합 검색·상세 조회와 실행 로그를 확인했습니다.
- 초기 Real 스모크 테스트는 합성 우산 인식과 구조화 출력 문제로, 첫 전구 시도는 개인정보 모델의 과차단으로 게시 전 단계에서 멈췄습니다. 이후 같은 전구 초안을 수정·재검증하여 게시에 성공했습니다. 별도 이미지를 사용하는 경우 `LAF_REAL_TEST_PHOTO`에 테스트용 이미지 경로, `LAF_REAL_TEST_ITEM_NAME`에 확인할 물품명을 지정할 수 있습니다.

OpenCV는 주로 정면 얼굴을 검출하며 작은 얼굴, 측면 얼굴, 화면 속 사진은 놓칠 수 있습니다. 맥락 판정과 재검사를 함께 실행하지만 OCR과 VLM이 동시에 놓친 개인정보까지 검출한다는 보장은 없습니다. 일반 숫자 연속열 규칙은 일부 무해한 제품번호도 가릴 수 있습니다. 내부 DB 접근 제어, 원본 암호화, 백업 보존 주기와 삭제, 역할 분리와 정량 검출 정확도 평가는 운영 도입 시 별도로 검증할 범위입니다.
